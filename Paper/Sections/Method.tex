\section{Contribution}

\subsection{Overview}

Our work presents a practical and lightweight approach to automatic materialized view selection through a PostgreSQL\textcite{postgresql_2026} extension that operates directly within a live database system. The framework combines information collected from PostgreSQL's query monitoring infrastructure, incremental view maintenance support, and a custom extension responsible for materialization decisions. Unlike many existing approaches that require extensive configuration, offline training, or application-level modifications, our system continuously observes query traffic and automatically determines which views should be materialized. The design is entirely self-contained within the database engine and adapts online as workload characteristics evolve, requiring no training data or manual intervention.

Our extension identifies high-cost data access patterns and proactively constructs materialized views to optimize future read operations. Rather than relying on manual database administrator intervention, we employ a continuous background monitoring process that evaluates historical workload telemetry to make view materialization decisions.

To minimize computational overhead and avoid generating views for transient or negligible queries, the algorithm applies a strict pre-filtering mechanism. A query $q$ is considered a candidate for materialization only if it surpasses the frequency threshold $T_{freq}$ (the number of times the query is executed) and the latency threshold $T_{lat}$ (the query's mean execution time).

Once the candidate queries are identified, the system evaluates their materialization utility using a heuristic scoring function, which can be configured based on different workload characteristics. In the default implementation, the utility score is calculated as the number of invocation times the mean execution time. This heuristic prioritizes to materialize expensive queries that are frequently invoked.

Given the maximum view capacity $k$, the system selects the top $k$ highest-scoring queries for materialization. The materialized views are stored in the shared-memory registry and subsequent queries are redirected to examine the materialized views.

\subsection{Advantages over related works}

We claim that our system offers several advantages over existing approaches to materialized view selection in the following aspects:

\begin{itemize}

\item \textbf{Operational simplicity.} Recent research has explored using machine learning models to select materialized views, but such systems often introduce substantial computational and deployment overhead. Training and inference may require specialized hardware such as GPUs or AI accelerators that are rarely available on production database servers, which are typically CPU-only environments optimized for transactional and analytical workloads. Integrating a separate machine learning infrastructure with a database deployment can significantly increase system complexity and operational cost. In contrast, our framework relies exclusively on lightweight CPU-based heuristics whose decision-making process is transparent and interpretable. As a result, the system can be deployed on existing PostgreSQL installations without additional hardware requirements or black-box model dependencies.

\item \textbf{Measuring actual system performance rather than relying solely on database cost estimates.} Many previous studies evaluate materialized view selection techniques using the query optimizer's internal cost model as a proxy for execution time. However, these cost estimators are based on simplified assumptions, including uniform data distributions and statistical independence between attributes, which often do not hold in real-world datasets. Furthermore, optimizer cost models do not capture effects such as cache behavior, lock contention, operating-system scheduling, or concurrent workload interference. To address these limitations, our evaluation measures real wall-clock execution times obtained from concurrent clients interacting with a live PostgreSQL instance. Consequently, the reported improvements reflect performance gains that end users would directly experience in practice rather than improvements predicted by an analytical model.

\item \textbf{Operating effectively under dynamic workloads.} Existing view-selection methods frequently assume that query patterns remain stable over time, allowing a model to be trained once and subsequently deployed. Production database environments, however, are characterized by continuously changing access patterns driven by evolving application features, user behavior, and business requirements. To evaluate adaptability, we introduce a workload-shift experiment in which the dominant query patterns transition from one set of tables to another. The system automatically identifies the change, gradually reduces the importance of previously active tables, and reallocates materialization resources toward newly active data. This process occurs without administrator intervention, demonstrating the ability of the framework to track workload evolution in real time.

\end{itemize}

Our methodology further distinguishes itself by explicitly accounting for view-maintenance overhead. Materialized views improve read performance but impose additional costs on write operations because modifications to underlying tables must be propagated to the materialized view. In our implementation, this maintenance is performed through incremental view maintenance mechanisms that execute during update operations. While many prior studies ignore maintenance costs or approximate them using simplified formulas, our evaluation measures the actual runtime overhead introduced by live maintenance operations. Consequently, the reported results capture the true tradeoff between accelerated query execution and increased update cost, providing a more realistic assessment of net system benefit.

Finally, the benchmark developed for this study constitutes a contribution in its own right. We construct a reproducable evaluation framework based on a realistic six-table schema, intentionally unindexed foreign-key relationships, and multiple workload classes representing distinct database access patterns. The benchmark includes join-intensive analytical queries, wide-table access patterns, aggregation workloads, and mixed transactional scenarios. In addition, the workload-shift experiment provides a reproducible mechanism for evaluating a system's ability to adapt to changing query distributions over time. By releasing a practical baseline that measures real database performance under diverse conditions, this benchmark establishes a foundation against which future heuristic and machine-learning-based view-selection techniques can be compared.
